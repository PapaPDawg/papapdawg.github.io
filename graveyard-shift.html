Graveyard Shift

A cozy, melancholy relationship sim about working the night shift at a cemetery, built in Unreal Engine 5 with modular, data-driven gameplay systems.

Status: Active development (vertical slice). Graveyard Shift is a working title.

Overview

Players work the evening shift as a cemetery caretaker. Harold, the aging groundskeeper, hands out the night's chores. The graveyard holds ghosts with unfinished stories, and at the end of every shift Grandma picks the player up for a quiet drive home. Those drives are a place to decompress and reflect between heavier moments.

The project is also a demonstration of how I build gameplay systems: clear ownership of responsibilities, event-driven communication, and content kept in data rather than hard-coded into actors. Each feature is built as a reusable system that can grow with the game.

Gameplay Loop

Start the Shift

Talk to Harold. He introduces himself on the first night, then hands out each night's randomized chores.

Maintain the Grounds

Pick up trash, pull weeds, and clean neglected graves across the cemetery. Check in with Harold for a live progress report.

Meet the Spirits

Talk to the ghosts who linger in the cemetery. Each one has its own relationship progress and story. Ghost encounters and story arcs are currently in development.

Report Back

Return to Harold when the work is done and collect your pay.

The Drive Home

When Grandma arrives, leave through the gate for the drive home, then return for the next night's shift.

System Breakdowns

Data-Driven Dialogue System

Problem: The first dialogue system was built around one character. Lines lived on the actors placed in the level, and the controller cast to one specific NPC class. Two problems came out of that. A per-instance override on one placed actor quietly blanked a line of dialogue. And when the controller started casting to a living-NPC class, ghosts silently lost the ability to talk.

Approach:

  • A reusable dialogue component owns the whole conversation lifecycle: selection, line advancement, time pausing, movement locking, and cleanup.
  • Each speaker's content lives in a Data Asset. Entries carry conditions: minimum day, minimum affinity, play-once, and priority.
  • A Gameplay Tag Context lets situation-driven characters request a kind of conversation, such as Harold asking for "Progress." The selector then picks the best matching entry for the current day.
  • Runtime lines, like live chore counts, are added after an entry's own lines without changing the asset.
  • An end-of-dialogue event dispatcher reports which conversation ended and whether it was finished. The speaker reacts by assigning chores or paying the player.
  • Completed play-once conversations are stored in the Game Instance, so they stay completed across level changes.

Debugging highlight: After the migration, Harold never started the chores even though the assignment conversation finished. Step-by-step checks showed the event was firing but always reported "not completed." The cause was a member variable that shared its name with the function's input. The dispatcher was reading the variable instead of the real value.

Result: Any actor with the component can talk, with no casts to specific classes. A new character needs one Data Asset and one component. Harold's entire workday (intro, assignment, progress, payment) runs on this system.

Randomized Daily Chores

Problem: Each night needed a different amount of work in different places, without the same spot being used twice.

  • A chore manager rolls a random count for trash, weeds, and dirty graves at the start of each day.
  • Spawn points are shuffled and then picked by loop index, which guarantees unique locations. Random-index picking had caused duplicates.
  • Graves already exist in the world. Instead of spawning anything, selected graves switch to a dirty state that the player can interact with.
  • One progress function reports totals and completed counts to anything that needs them, including Harold's live progress lines.
  • Chores are assigned when Harold's assignment conversation completes, and they regenerate each new day.

Ghost Affinity and Persistence

Problem: Every ghost needs its own relationship value. The tutorial ghost's progress has to reflect the player's progress with every other ghost.

  • A shared ghost parent class owns affinity, with changes clamped to 0–100, so each child ghost holds its own independent value.
  • An affinity-changed dispatcher announces every change without tying the ghost to any particular UI, dialogue, or story system.
  • The tutorial ghost listens to every other ghost's dispatcher and recalculates its own affinity as their average. It can only reach 100% once every other ghost has.
  • Each ghost has a stable ID. Affinity is saved to and restored from the Game Instance, with a "found" flag that separates "saved at zero" from "never saved."

Other Systems

  • Tap / Hold / Talk interaction framework, with each input phase handling a specific interaction type
  • 12-hour in-game clock with an overtime warning and automatic end of shift
  • Multi-day loop with daily pay and money that persists between levels
  • Material-driven iris transition with fade-complete event dispatchers
  • Cross-level flow between the graveyard and a dedicated drive-home level, orchestrated by a drive manager
  • Modular vehicle actor with seat and camera attachment points

Engineering Highlights

  • Content lives in data (Data Assets and Gameplay Tags), so new characters and conversations don't need new Blueprint logic.
  • Components and event dispatchers replace class-specific casts and timing-based delays.
  • Each system has a clear owner. For example, the chore manager owns chore data, Harold decides what to say, and the dialogue component handles how it's said.
  • Game state that must survive level changes lives in the Game Instance.
  • I debug step by step and keep a dated development changelog that records each problem, its cause, the fix, and the result.
